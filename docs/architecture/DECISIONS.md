# Architecture Decision Records (ADRs)

**Last Updated**: 2026-07-31

This file documents key architecture decisions for Prospecção Brasil. Each
ADR follows the template: Context, Decision, Rationale, Alternatives
Considered, Consequences.

---

## ADR-001: Go + HTMX monolith over SPA

**Date**: 2026-07-31
**Status**: Accepted

### Context

Prospecção Brasil needs a web application with an institutional front-end
(premium credibility) and an internal system (property/client management).
The team is small (single developer + AI agent). The MVP must ship fast with
minimal complexity.

### Decision

Build a server-rendered monolith using Go + HTMX + Alpine.js + Tailwind CSS.
No SPA, no React, no separate frontend/backend repos.

### Rationale

- **Single binary deployment**: Go compiles to one binary. No Node.js
  runtime in production, no separate API server, no CORS issues.
- **HTMX for interactivity**: HTMX provides AJAX, partial page swaps, and
  inline editing without a JS framework. The server renders HTML fragments;
  HTMX swaps them in. This keeps the logic server-side (Go) and the client
  thin.
- **Alpine.js for micro-state**: Dropdowns, modals, tabs -- Alpine.js handles
  small client-side state without a full framework.
- **Tailwind for styling**: Utility-first CSS, compiled at build-time (no
  runtime CSS-in-JS). Self-hosted output.
- **Small team**: A monolith is easier to reason about, deploy, and debug
  than a distributed system. One repo, one binary, one database.
- **No CDN dependency**: HTMX and Alpine.js are self-hosted in `static/js/`
  (no CDN SPOF).

### Alternatives Considered

- **React SPA + Go API**: More complex (two build systems, API design,
  state management, CORS). Rejected for MVP because: doubles the codebase,
  slower iteration, harder to SEO for the institutional site.
- **Next.js (React SSR)**: Adds Node.js runtime, more complex deployment,
  less type safety end-to-end. Rejected because: Go is the primary language;
  mixing Node.js adds operational complexity.
- **Ruby on Rails / Django**: Productive but adds a second runtime. Go was
  chosen for single-binary deployment and strong typing.

### Consequences

- All UI is server-rendered HTML. Interactivity via HTMX (AJAX swaps) and
  Alpine.js (micro-state).
- No client-side routing (all routes are server-side).
- SEO is straightforward (server-rendered HTML is indexable).
- JavaScript bundle is tiny (~92KB: HTMX 48KB + Alpine 44KB, self-hosted).

## ADR-002: sqlc over ORM

**Date**: 2026-07-31
**Status**: Accepted

### Context

The application needs typed database access in Go. The schema has 8 tables
with multi-tenant isolation (tenant_id on every tenant-scoped query), CHECK
constraints, and LGPD-sensitive PII fields.

### Decision

Use sqlc to generate typed Go from SQL queries. No ORM (no GORM, no
ent, no sqlx). SQL is the source of truth.

### Rationale

- **SQL is the source of truth**: sqlc reads SQL queries from
  `internal/db/queries/*.sql` and generates typed Go functions. The SQL is
  reviewed and tested -- not hidden behind an ORM abstraction.
- **Type safety**: sqlc generates structs and function signatures from the
  SQL. If a query references a column that doesn't exist, sqlc fails at
  code-generation time (before tests).
- **Performance**: sqlc generates raw `database/sql` or pgx code -- no
  reflection, no struct-tag parsing at runtime.
- **Multi-tenant safety**: Every query is written with `AND tenant_id = $X`
  in SQL. The generated Go function requires the tenant_id parameter --
  you cannot forget it. An ORM makes it easy to forget a WHERE clause.
- **LGPD audit**: SQL queries are grep-able. `grep -r "UPDATE audit_log"
  internal/db/queries/` verifies append-only enforcement. An ORM hides
  queries behind method chains.

### Alternatives Considered

- **GORM**: Popular Go ORM. Rejected because: hides SQL, makes it easy to
  forget tenant_id filters, runtime reflection, harder to optimize queries.
- **ent**: Schema-first code generation. Rejected because: adds a DSL
  (ent schema) on top of SQL; sqlc uses SQL directly (no new language to
  learn).
- **sqlx**: Thin wrapper over database/sql. Rejected because: no code
  generation -- you write struct scanning by hand, no compile-time type
  safety on query results.

### Consequences

- All database access goes through sqlc-generated functions in
  `internal/db/`.
- Adding a new query: write SQL in `internal/db/queries/<entity>.sql`,
  run `make sqlc`, use the generated function.
- Generated files are gitignored (regenerated by `make sqlc` and CI).
- No runtime migrations (schema changes require a forward-only migration +
  sqlc regenerate).

## ADR-003: Self-hosted JS libraries over CDN

**Date**: 2026-07-31
**Status**: Accepted

### Context

The front-end uses HTMX and Alpine.js for interactivity. These libraries
are typically loaded from a CDN (unpkg, jsdelivr). However, CDN dependencies
create a single point of failure (SPOF): if the CDN is down or slow, the UI
degrades (modals, tabs, partial swaps stop working).

### Decision

Self-host HTMX and Alpine.js in `static/js/`. Pin to specific versions.
Reference them via `<script src="/static/js/htmx.min.js" defer></script>`.

### Rationale

- **No SPOF**: If a CDN is down, the UI still works. The only dependency
  is the application server itself.
- **Privacy**: No third-party requests (CDNs track users via Referer
  headers). LGPD-friendly.
- **Performance**: Self-hosted files are served from the same origin as
  the app -- no DNS lookup, no TLS handshake to a CDN. ~92KB total (HTMX
  48KB + Alpine 44KB), gzipped.
- **Reproducibility**: Pinned versions in `static/js/` are version-
  controlled. No surprise updates from `@latest`.

### Alternatives Considered

- **CDN (unpkg/jsdelivr)**: Simpler to update (change a URL). Rejected
  because: SPOF, privacy concerns, external dependency for a core UI
  function.
- **npm bundle (esbuild/webpack)**: More complex build pipeline. Rejected
  because: HTMX and Alpine are standalone files -- no bundler needed for
  2 files.

### Consequences

- `static/js/htmx.min.js` (v1.9.12, 48KB) and `static/js/alpine.min.js`
  (v3.14.1, 44KB) are committed to the repo.
- Updating a library: download the new version, replace the file, update
  the version comment, test.
- The static file server in `cmd/prospeccao/main.go` serves `static/js/`.
- No `@alpinejs/trap` plugin (depends on npm `focus-trap`); implement
  focus trap manually with Alpine directives.
